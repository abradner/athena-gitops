athena-gitops · cluster/zagreus/waker

zagreus waker

One pod on zagreus's control plane runs this loop every 30 seconds. It keeps the two amd64 runner nodes asleep until the always-on classic runners can't keep up. It wakes them through Intel AMT when work queues, and puts them back to sleep after an hour idle. All along, it tells GitHub how many jobs each zagreus scale set may take.

Why maxRunners, not only power

GitHub offers an ARC scale set as many jobs as its maxRunners allows, whether or not its pods can schedule. A job a set claims is bound to that set. Probes on spritz on 23 Oct 2026 showed it:

RunScale setWhat happened
39882337983maxRunners: 1, no node it could schedule onClaimed a job. The job waited on a Pending pod while an idle classic runner sat beside it.
39883352061maxRunners: 0Offered nothing. Every job went to the classic runner.
39883642252raised to 1 on the live setListener restarted in about 8 s and claims resumed.

The rule: live maxRunners = what the awake, schedulable nodes can actually run, never above the ceiling written in the set's Argo Application. While the nodes sleep, it is 0.

Argo ignores spec.maxRunners on the three driven sets (zagreus-ci, zagreus-ci-x64, zagreus-docker-amd64), with RespectIgnoreDifferences, so a sync never writes the ceiling back over the waker's value.

One pass

Waker.tick() runs every pollSeconds (30). It is single-threaded, and a wake or a sleep runs inside the pass that chose it, so there is never more than one at a time.

flowchart TD
  A[observe: nodes, Leases, pods, scale sets, Applications, runners, asleep list] --> B{mode full?}
  B -- yes --> C[take back Ready nodes left asleep or cordoned; audit the asleep list; renew it]
  B -- no --> D
  C --> D[update idle and awake clocks]
  D --> E[apply_caps: write maxRunners to what the awake nodes can run]
  E --> F[read GitHub: queued spritz jobs]
  F -- unreadable --> H[hold: no wake, no sleep]
  F --> G[unmet demand per set]
  G --> W{a sleeping node has room for unmet demand?}
  W -- yes, not in cooldown --> WK[wake it - full mode only]
  W -- no --> S{a node idle 60 min, nothing unmet it serves, no unplaced runner?}
  S -- yes --> SL[put it to sleep - full mode only]
  S -- no --> Z[next pass]

What it reads

Every pass starts from the cluster as it is. Nothing the waker relies on lives only in its own memory.

  • Each configured node:
    • Ready is the Ready condition, the kubelet's Lease renewed in the last 25 s, and Ready since any shutdown the waker stamped (node_fresh_ready).
    • The Lease time is the API server's own stamp on the kubelet's update (managedFields[].time), from the control plane's clock, so a worker's skewed clock can't fool it.
    • Unschedulable is a cordon or any NoSchedule/NoExecute taint the runners don't tolerate.
    • It also reads the node's free room, allocatable less every pod's requests, and the driven-set runners already on it.
  • Each driven scale set: its live maxRunners, its labels, and its pod requests from the template (the builder's dind sidecar counts in full). Its ceiling comes from the Argo Application, falling back to the last ceiling read. It also reads its EphemeralRunners: how many, how many haven't started a job, and how many aren't on a node yet.
  • The asleep list is the ConfigMap log-heartbeat/waker-asleep. Only full mode reads it.

Caps

compute_caps gives each set the room it can actually use, then bound_caps holds it under the ceiling.

  1. Claimed but unbound runners first. A runner a set has claimed whose pod isn't on a node yet still needs room. It is placed on paper on an awake node it fits, preferring one where its set has slots. If it fits nowhere, it adds nothing.
  2. Each awake node, for each set in waker.conf order:
    • the set's own runners there count;
    • then it gets no more than its configured slots minus those runners, and no more than fits in what is left of the node.
    The builder is listed first because it preempts CI pods.
  3. The ceiling. If no ceiling has ever been read, caps only go down.

Two worked examples

  • 01 gone, an e2e job (6 GiB) running on 02. 02 has room for one more heavy pod, so zagreus-ci gets 1 and zagreus-ci-x64 keeps 1 for its running job. Before room counting, it would have offered ci 2, and one of those two jobs would have been stranded.
  • 02 cordoned by hand (live, 24 Oct 21:46). zagreus-ci maxRunners 3 -> 1 was written 18 s later and held for 3 h. It went back to 3 within 32 s of 02 being Ready again.

Lowering is immediate. The one exception is the first pass after a start: if that pass can't read a node's Lease and has nothing earlier to go on, it waits a pass before lowering, so one failed read doesn't make the listeners flap.

Demand

The waker lists queued jobs in spritz's queued and in-progress runs, using ETags (GitHub doesn't charge a 304 against the rate limit) and reading every page. A job is demand for a set when the set carries every label the job asks for.

  • A job that names a set (runs-on: zagreus-ci) counts at once: no classic runner carries a set's name.
  • A shared-label job counts after 60 s queued. An idle classic runner with those labels takes a job within seconds, so one still waiting means no classic runner is free.
unmet = demand − claimed − spare
  claimed = min(runners not yet running a job, demand)   # GitHub still lists them as queued
  spare   = maxRunners − runners                          # GitHub fills this within seconds

Finished runners (Succeeded or Failed but not yet cleaned up) are left out of runners and claimed, so they can't hide demand (athena-gitops#239).

Wake

A wake happens when a set has unmet demand, or a runner it has claimed has been waiting more than 60 s with no room on any awake node, and a sleeping node has a slot for it. It picks the first such node in waker.conf order, wakes one node at a time, and then waits a 180 s cooldown. A node whose last wake failed is retried after a 30 min backoff.

sequenceDiagram
  participant W as waker
  participant A as AMT (port 16992)
  participant K as API server
  participant L as asleep list
  W->>K: annotate waking
  W->>A: RequestPowerStateChange(2)
  A-->>W: PowerState 2
  W->>K: wait: Ready, fresh Lease (up to 10 min)
  W->>K: wait: heartbeat pod Ready
  W->>L: remove the node
  W->>K: uncordon
  W->>K: raise maxRunners

If any step fails, the node comes off the asleep list, so its silent heartbeat raises ZagreusNodeKmsgGone. It is annotated wake-failed and retried later.

The AMT proof on 23 Oct 2026: zag-amd64-02 went from shutdown to S5 in 36 s, from power-on to AMT on in 19 s, and from power-on to Ready in 51 s.

Sleep

A sleep happens to the last node in order that has been idle for 60 minutes, while no set it serves has unmet demand, no runner is waiting for a node, every ceiling is known, and the pass isn't degraded. The node must also be one the waker can wake again (AMT, or Wake-on-LAN). "Idle" means no pod other than DaemonSets, static pods and kube-system. An idle warm runner still holds its node.

sequenceDiagram
  participant W as waker
  participant K as API server
  participant L as asleep list
  participant T as Talos API
  participant A as AMT
  W->>K: lower caps as if the node were gone; wait 15 s
  W->>K: cordon; wait 30 s; any pod landed? abort
  W->>L: add the node; wait 180 s; any pod? abort
  W->>K: stamp waker-slept-at
  W->>T: shutdown (os:operator)
  W->>A: wait for PowerState 8 (5 min)
  Note over W,A: still on: AMT hard off; still unconfirmed: back on the list, backoff
  W->>K: annotate asleep

A failed talosctl call isn't treated as "still on" by itself: the node may be going down anyway. Only AMT reporting it on aborts the sleep. Without AMT, "off" means the kubelet's Lease has stopped, plus a 30 s margin, and a Lease that can't be read never counts as off.

The asleep list and the alerts

ZagreusNodeKmsgGone fires for any zagreus node whose kernel-log heartbeat goes quiet. A node the waker puts to sleep must leave that alert's expected list before its power goes. zagreus has one road to the log store, Talos's kernel-log sender, so the list travels on it:

  1. The waker writes log-heartbeat/waker-asleep, with asleep, emitter (its own node) and renewed. It renews it every pass, and every 30 s inside a long wake or sleep.
  2. On the emitter node only, the heartbeat DaemonSet writes log-pipeline asleep <node> into the kernel log each minute. It does this only while renewed is under 5 minutes old, and only for names that are DNS labels (globbing off, at most 8).
  3. asn-infra records those lines from cp1 only, as talos:waker_asleep_by_node. The receiver sets node from the connection, so no other node can vouch for one. Both alerts leave out a node asserted in the last 150 s.

Measured on 25 Oct: a dummy name took 170 s from the ConfigMap to obs-metrics, inside the 180 s publish lead.

If the waker dies, renewals stop. The relay goes quiet after 5 minutes, and every sleeping node starts alerting. A dead waker can't leave nodes silently unwatched.

When reads fail

Every guess goes the safe way. Under-offering only sends jobs to the classic runners; over-offering strands them.

Can't readWhat the pass does
GitHub (an error, or rate-limited until the reset)Holds: no wake, no sleep. Caps still follow the nodes. After 15 minutes without a good read, it stops renewing the asleep list, so sleeping nodes alert instead of waiting silently while jobs queue.
One nodeThat node counts for nothing this pass.
One scale setThe pass is degraded: caps may go down, never up, and nothing sleeps.
A set's runner listIts demand wakes nothing, and an unplaced runner is assumed, which blocks sleep.
An Application (the ceiling)Uses the last ceiling read. With none ever read, caps only go down and nothing sleeps.
A pod's or template's requestsThat node or set offers no new slots.
A node's LeaseReuses the last good reading for up to 60 s from the renewal it describes, then the node counts as gone. During a sleep's off-wait, an unreadable Lease is never "off".

Operating it

# what it is doing
kubectl -n zagreus-waker logs deploy/zagreus-waker -c waker --tail=50
# wakes, sleeps and their timings
kubectl -n zagreus-waker get cm waker-events -o jsonpath='{.data.events}'
# what it has put to sleep
kubectl -n log-heartbeat get cm waker-asleep -o yaml
# power by hand, with the pod's own credentials
kubectl -n zagreus-waker exec deploy/zagreus-waker -c waker -- python3 /opt/waker/waker.py amt-status zag-amd64-02
kubectl -n zagreus-waker exec deploy/zagreus-waker -c waker -- python3 /opt/waker/waker.py amt-on zag-amd64-02

Rollback:

  1. Set mode back to caps or observe and merge.
  2. Power any sleeping node on (amt-on) and uncordon it.
  3. If the waker is going away entirely, patch each set's maxRunners back to its ceiling by hand. With RespectIgnoreDifferences, an Argo sync keeps the live value. The exact commands are in the README.

How it is tested

100 unit tests run against fakes of the API server, GitHub, AMT and talosctl, which record every write in order. That lets a test check what happened before the power went, not only that it went. The fakes keep a shut-down node Ready for about 45 s, the way the API server does, and stamp Leases with the control plane's clock. Each guard was proven by mutation: remove it, watch its test fail, restore it.
